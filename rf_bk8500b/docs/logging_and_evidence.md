# Logging and evidence (RFDS-008)

`rf_bk8500b` records every public keyword call as structured evidence so a
failure can be diagnosed after the fact, without needing to reproduce it live.
This document describes what gets recorded, where it goes, and how it relates
to this driver's existing audit/metrics infrastructure. The implementation is
`bk8500b/evidence.py`.

## Relationship to existing infrastructure

This driver already had two logging-adjacent systems before this evidence
engine was added; neither is replaced:

- **`bk8500b.diagnostics.AuditSink`/`MetricsSink`.** `CommandExecutor` already
  calls `audit_sink.record(AuditEvent(...))` on every write/query transaction
  (operation name, risk class, outcome, timing) and `metrics_sink.increment/
  observe(...)` for counters. `EvidenceAuditSink`/`EvidenceMetricsSink` in
  `evidence.py` *implement* those same protocols and forward into the
  evidence run — connecting evidence recording to the executor is one
  constructor argument (`BK8500BLibrary._default_device_factory`), not a
  second system competing for the same seam.
- **The archived `evidence/hardware_conformance/<release>_<port>_<date>/`
  directories** used by sibling drivers in this repository (see e.g.
  `rf_bk8500_load`) are point-in-time summaries generated by post-processing
  a completed Robot `output.xml` after a real hardware run. What's described
  here is different: a live, always-on, per-session system that also works
  outside a formal Robot suite run (e.g. from a plain Python script).

`AuditEvent` records a transaction's *outcome*, not the literal bytes sent or
received. The one genuinely new capability this evidence engine adds at the
protocol level is `TracingTransport`, which wraps the real serial transport
and hex-encodes every byte written/read — the true RFDS-019 protocol-boundary
observation point for this driver's SCPI text and 26-byte legacy binary frame
protocols alike.

## What gets recorded, and where

One evidence **run** covers one `BK8500BLibrary` instance (its `SUITE` scope),
from the first keyword call until every connected alias has disconnected,
written to:

```text
results/session/rf_bk8500b/<UTC timestamp>_<run_id>/
├── run_summary.json          # authoritative: final status, error/warning counts, duration
├── run_summary.md            # human-readable derived summary
├── environment.json          # Python/Robot/driver versions, sanitized host token
├── device_identity.json      # manufacturer/model/serial/firmware — written per successful connect
├── evidence_manifest.json    # one entry per artifact below, with a SHA-256 hash each
├── events/
│   ├── events.jsonl          # every lifecycle event, including forwarded AuditEvents
│   ├── operations.jsonl      # one entry per keyword call: arguments, duration, result, status
│   └── errors.jsonl          # one entry per raised exception: category, message, traceback
├── protocol/
│   ├── exchanges.jsonl       # every outbound/inbound wire exchange, machine-readable
│   ├── outbound_trace.log    # the same, human-readable (driver -> instrument)
│   └── inbound_trace.log     # instrument -> driver
└── integrity/
    └── checksums.sha256      # sha256sum-compatible list of every artifact above
```

Override the root with `RFDS_EVIDENCE_ROOT` (default `results`, relative to
the current working directory). A multi-alias suite (several loads connected
at once) shares one run; individual events/operations/protocol exchanges are
still tagged with the resolved `session_alias` so per-instrument evidence
remains attributable.

## Reading a failure

1. Open `run_summary.json` — `final_status`, `error_count`, and
   `evidence_completeness`.
2. Open `events/errors.jsonl` — one JSON object per exception, `category`
   (`VALIDATION`, `STATE`, `SAFETY`, `HARDWARE`, `UNKNOWN`), exception
   type/message, full traceback.
3. Cross-reference `operation_id`/`correlation_id` into
   `events/operations.jsonl` for the exact keyword call (arguments included),
   and into `protocol/exchanges.jsonl` for the raw SCPI text or legacy frame
   bytes that operation actually sent/received before failing.
4. `protocol/outbound_trace.log`/`inbound_trace.log` give a plain
   chronological read of every wire exchange without parsing JSON.

## Enabling/disabling it

On by default. Disable with:

```robotframework
Library    BK8500BLibrary    evidence_enabled=${FALSE}
```

Errors still reach the standard Python logger and Robot's own log either way
— only the structured run directory is skipped.

## Exporting a diagnostic bundle

```robotframework
${path}=    Export Diagnostic Bundle
Log    Diagnostic bundle written to ${path}
```

Zips the current run (refreshing its manifest first) without finalizing it —
useful mid-session, before any `Disconnect*` keyword, when troubleshooting
something that hasn't finished failing yet.

## What this system deliberately does not do

Consistent with the `rf_phidget_relay` reference implementation this was
adapted from: no shared cross-driver evidence package (none exists yet in
this repository), no log rotation/backpressure policy (this driver's event
volume doesn't need it), no cryptographic signing or archival automation, and
no literal RFDS-007 error codes (RFDS-007 wasn't available while writing
this; `category` in `errors.jsonl` is a pragmatic mapping of this driver's
own `bk8500b.exceptions` hierarchy).

## Validating a run's integrity

```console
python scripts/validate_evidence.py results/session/rf_bk8500b/<run>/
```

Recomputes every SHA-256 hash in the manifest, checks every JSONL stream is
valid JSON with a gap-free monotonic `sequence`, and confirms
`run_summary.json` is internally consistent.
